# 数据采集总控台

唯一交互入口是 [console.py](console.py)。它使用 PySide6 / Qt Widgets 独立桌面窗口提供环节选择、原 CLI 参数表单、单项直接运行、批量命令预览、监控、历史查看及维护工具。
执行内核在 [runtime/background_worker.py](runtime/background_worker.py)，业务采集仍由 b01—b04 原文件负责。
强制规则见 [AGENTS.md](AGENTS.md)，项目规则见 [采集 AGENTS](../AGENTS.md)，业务影响见 [采集 README](../README.md)。

## 打开与使用

先按[环境说明](../../../environment/README.md)配置 `latitude_env_v2`；PySide6 版本以 [requirements.txt](../../../environment/requirements.txt) 为准。在仓库根目录启动：

```powershell
Set-Location -LiteralPath 'E:\Latitude_Analytics_v2'
& 'E:\anaconda3\envs\latitude_env_v2\pythonw.exe' 'E:\Latitude_Analytics_v2\02_Market_Data\a01_Collection\operations\console.py'
```

打开窗口默认进入 b00，只读取源码参数和历史证据，不调用业务 API。进入 b01/c01“日历结果”页后，会按下述结果展示边界只读加载交易日历；页面不写业务湖。若需要查看启动错误，可用同环境 `python.exe` 替代 `pythonw.exe`。

右上角单个太阳／月亮图标按钮切换整个总控台及弹窗的外观：太阳表示切换到亮色，月亮表示切换到暗色，悬停提示说明目标主题；支持键盘聚焦和空格操作。首次默认亮色。选择通过 Qt QSettings 保存在当前 Windows 用户的 `HKEY_CURRENT_USER\Software\LatitudeAnalytics\FuturesOperations` 下，仅保存 `appearance/theme`；不保存业务参数，也不改动批次请求。重开后恢复上次主题。

顶部为“采集工作台”“运行监控”“历史批次”；打开默认进入 b00 运行环境页。b00 不参与业务批量勾选。左侧搜索只过滤显示，隐藏的已选环节仍计入预览。右侧显示原文件简介，可切换参数与完整说明并拖动分隔条。底部显示批量选择数量；无勾选项时批量预览禁用，当前环节仍可单独运行。

监控页显示状态、耗时、心跳、阶段、当前对象与局部进度，日志默认跟随当前阶段，手动选择后可恢复跟随。历史按启动时间倒序、北京时间显示，悬停保留原 UTC；刷新显示时间、条数及最新启动时间。有请求或启动证据但无状态的批次显示“未发布状态”或“启动失败”，不推断成功。

“返回本窗口批次”只导航到本窗口最近启动的批次，不重新执行或恢复；无目标或已在目标时禁用并说明原因。查看其他历史时仍显示本窗口活跃批次的阶段、进度、耗时和心跳；重开窗口不接管旧任务。

1. 点击环节查看参数和原文件说明；b01/c01 默认打开“日历结果”，c02—c04 打开对应运行看板，均可切换“运行参数”和“完整环节说明”。单独运行不要求勾选；准备多选批次时，点击环节前的复选框或按空格勾选。19 个正式环节均可单独运行；多选仍按 b01—b04 和组内文件顺序执行。不会自动追加上游。
2. 逐个配置原文件参数。空白字段沿用原 CLI 默认值，布尔参数由勾选控制；多值参数用英文逗号分隔。参数类型、范围、默认值、必选条件直接读取原 Click 声明；业务源码不被导入或执行。动态回调/动态默认值不能静态读取时明确报错。
3. “日常更新配置”选中日常 18 个环节，并默认开启它们的 `--write`；保留其他已编辑参数，之后仍可逐项取消写入。按钮只配置本批，不直接启动。初次打开且未点击该按钮时，表单仍沿用原文件默认值。该按钮不选择 c08，也不修改其参数；c08 必须人工单独选择并确认原参数 `--confirm-full-quality`，提交需另选 `--write`。各文件原有 `--full`、`--force`、配额和仓单性能参数均在其表单内。
4. 只运行当前页时，检查屏幕显示的原参数与写入意图，然后点击“运行此环节”，即直接授权并启动这个单项批次，不再出现额外预览确认。其他批量勾选项不会被运行，也不会被取消。成对日期、正式湖范围、仓单参数配对及上游就绪条件仍由原入口检查；只读业务运行仍可能请求来源 API。
5. 多选批次使用“预览本批命令”，核对逐项命令、有效参数和写入意图，再点击“启动本批次”。单项和多选都生成全新批次目录并由同一后台 worker 执行；参数与源码摘要随 request 固定，运行中编辑表单不改变本批。
6. 在“运行监控”查看三个业务 preflight、各业务阶段、耗时、心跳、步骤、当前对象和实时日志。preflight 失败会集中显示失败项和“业务尚未开始”；未执行阶段明确没有日志。环节非零退出、配额停止或监控失效会停止后续环节；业务脚本内部的既有窗口处理策略见下文。阶段数量不代表总耗时百分比。
7. “请求中断本窗口批次”只对本窗口启动的活跃批次写入一次 `interrupt.request`，查看历史不会改变中断目标。窗口保持可见直到后台停止；点击窗口关闭会询问是否请求中断并在停止后退出。进程被强行关闭或界面心跳超过 12 秒失效则作为监控故障停止，保留现场。

## b00 准备与检查

b00 分组左侧仅保留 `b00_01`—`b00_04` 四项。`b00_01` 页内提供“运行环境”和“辅助检查 · Windows 控制面”，后者明确标注实际脚本归属 `operations/runtime/verify_operations_runtime.py`。`b00_02` 页内切换“代码检查／完整检查／导出同步”。`b00_03`、`b00_04` 保留各自的共用模块流程与职责页。

页内模式只改变展示，在本窗口内记住选择；重新读取采集参数后也保留。点击执行仍只运行当前模式对应的固定命令，不接受任意脚本路径或自由拼接参数：

| 工具 | 执行内容 | 写入范围 |
|---|---|---|
| Python 运行环境 | `b00_01_verify_runtime.py` | 不写业务湖 |
| Windows 控制面 I/O 检查 | `runtime/verify_operations_runtime.py` | 仅控制面临时路径的 I/O 验证 |
| Notebook 代码正文检查 | `b00_02_sync_notebook_exports.py --check --check-level code` | 不修改导出文件 |
| Notebook 完整导出检查 | `b00_02_sync_notebook_exports.py --check --check-level full` | 不修改导出文件 |
| 重新生成完整 Python 导出 | `b00_02_sync_notebook_exports.py --write` | 四个正式业务目录下 19 个同名 `.py` 导出 |

代码检查比较 Notebook 默认导出与现有 `.py` 的 Python AST；docstring、字符串、参数和代码结构仍参与比较，注释、格式、单元格编号/位置不参与。它不会因为 Mermaid 或其他 Markdown 注释变化而单独阻断业务启动，也不代表完整文件已同步。完整检查保持默认 PythonExporter 输出逐字节一致要求；`--check` 未指定级别时默认为 `full`。

检查工具点击“执行检查”启动，并留在当前独立看板。完整同步点击“预览并同步”后展示目标文件范围和写入意图，再点“确认同步导出”才运行；始终用默认 PythonExporter 完整生成并复核，不以代码比较跳过文档/注释。同步结束后重新读取环节参数，按仍存在的参数名称保留当前输入和批量勾选；也可使用“重读采集参数”手动刷新。同步不执行 Notebook 单元格、不调用业务 API、不写数据湖。Notebook 修改后的正式同步和交付前完整检查要求保持不变。

`b00_01` 与 `b00_02` 页内的五种操作按实际工作流程展示看板：

- 运行环境：解释器与环境、核心依赖两步；逐项展示依赖版本与结果。
- Windows 控制面：长路径原子替换、共享读取与再次替换、Arrow 文件往返三步。
- Notebook 代码检查与完整检查：生成与语法验证、正文或字节比较两步。
- Notebook 导出同步：生成、写入、写后完整复核三步；逐文件分别展示各步结果。

每页同时显示第几步/总步数、步骤独立进度条、本步总量/已处理/剩余、异常项目、耗时与心跳；下方结果表和实时原始日志可拖动分隔条调整。小窗口可滚动工作页。已处理量包含失败项，不代表通过量；异常项目与具体失败原因独立显示。无计数时显示未知，不从日志位置推算比例。中断、失败与旧历史均不会补造成功。b00_03 与 b00_04 只呈现调用流程，没有虚构的运行百分比。

看板记住本窗口中各工具的运行目录，切换不会串入其他工具的状态或异步日志。历史记录继续通过“历史批次”进入通用只读监控；重开窗口不接管旧运行。窗口顶部在浏览任何页面时都持续显示本窗口活跃批次的阶段、可用计数、耗时与心跳。b01/c01—c04 已提供下述专属看板，其余业务入口保留原参数和通用监控。

所有维护任务使用相同后台 worker、全局锁、可见监控、中断和历史证据，但不附加三个业务 preflight，避免检查自身形成循环。检查失败不会自动修复文件；同步也不会自动接着启动采集。

b00_03 提供 Notebook 的 Schema/raw/有界样例展示；b00_04 由调用者决定事务范围和验收。二者无独立 CLI，页面只说明流程和打开源码，不提供执行或通用恢复按钮。四个 b00 文件均保持采集目录根级原位和编号。

## b01 的四个日历看板

交易日历的数据表头为 `英文字段名（中文含义）`，中文直接来自权威 Schema；更新时间列另注明北京时间。字段与数据保留原契约，遵循[展示规则](../../../AGENTS.md#数据呈现附带中文)。

左侧选择 c01 后默认进入“日历结果”：表格直接展示自然日、交易日标记、星期、周末、生效时点与更新时间，可切换全部 11 个原字段。表格上方显示本次结果、新增/修订或生成数量、提交状态及当前操作进度；`up_to_date` 明确显示“已是最新”、0 行更新及已覆盖日期，不再停留在未执行的流程卡片。c02—c04 继续使用六段流程与分步骤进度看板。原参数和完整说明均保留，单项启动后留在对应页面。

c01 可切换“已落盘日历”和“本批生成结果”，按年份、月份、交易日状态筛选，默认显示最新月份，日期倒序，每页 100 行。数据字段、表名和分区来自 `TRADE_CALENDAR_SCHEMA`。已落盘数据取自本次固定的 `--lake-root`，尚未运行时使用当前表单路径，未指定则读取 settings 的正式湖配置；表格明确标注来源及读取时间，不把当前表当成过去某批次的冻结快照。

结果读取在独立线程中完成，与日志/状态读取分离。只在进入页面、来源/批次变化、本环节结束或点击“刷新数据”时加载，最多 50,000 行，超限明确拒绝而不显示截断后的总量；筛选与分页在该快照上完成，不随每秒监控反复扫描。当前批次写入期间不重新读取已落盘表，结束后读取。生成预览缺失、目标尚未建表和读取失败分别显示；读取失败不改变 worker 的业务结果，可手动刷新。

“本批生成结果”来自该批次已通过业务验证的 Arrow 表，原子保存在 `artifacts/b01_generated.parquet`；预览失败只 warning，不改变业务结果。只读运行标注“尚未提交”，`--full` 展示完整期望而非仅差异行；预览与正式表的 `updated_at` 可不同，不能代替提交凭证。独立 CLI/Notebook 默认不生成附加预览；子进程变量隔离见 [AGENTS](AGENTS.md#维护工具与共用模块)。

| 页面 | 可量化的过程 | 提交边界 |
|---|---|---|
| c01 交易日历 | 日历结果表；本次生成、待写入、提交数量及当前操作进度 | 生成结果、事务内安装与事务成功退出分开 |
| c02 品种日历 | 交易日展开；当前事务分区合并及安装 | 全量模式可能有多个日期范围事务，分别显示最近一次 |
| c03 合约日历 | 合约信息请求批次；分区核对；当前分区品种日展开；正式叶提交 | 叶提交和处理水位确认分开呈现 |
| c04 行情日历 | 已有水位读取分组；基础分区规划；当前分区 1m/1d 结构；提交计划处理 | 处理数包含复核后跳过的 clean 叶，最终另列正式提交叶数 |

计数来自现有四个脚本的白名单日志，业务文件和取数方式不变。c01 的自然日范围在原脚本明确报告起止日后计量，完成量由实际生成行数确认。c01/c02 的 `partition_committed` 仍在共同事务内，不视为正式成功；只认事务外的 `committed`。c03 的单次信息响应完成不代表全部信息批次完成。c04 当前分区的 `2 / 2` 频率不会转换成整个脚本完成百分比。没有报告总量的步骤保持未知，流程节点也不按序号补造完成状态。

各页仅记住本窗口启动的对应批次；多选批次仍进入通用监控，可回到单页查看同批中的该环节。业务开始前显示准备检查状态与日志，不混用检查计数；其他业务阶段也不填充当前页数量。失败或中断保留最后记录和原始日志，不恢复或重试。历史仍通过通用只读监控查看。

## 目录与设计

`console.py` 是唯一交互入口，`runtime/` 的三个脚本负责执行与监督；没有第二套业务参数层，批次身份、目录、心跳和不可变命令清单由控制面生成。

界面、布局、配色和绘制图标集中在 `console.py`，不另设 UI、样式、组件或素材层。源码参数、历史与日志共用后台读取线程，c01 表格独立读取，Qt 主线程刷新控件和监控；切换主题不重建参数或改变命令。Windows 使用独立任务栏身份，窗口、弹窗与品牌区统一 Latitude 图标。开发约束见 [AGENTS](AGENTS.md#职责与唯一参数来源)。

## 监控与状态

- `request.json`：操作者确认的单项/批量业务或维护任务、参数与目标脚本 SHA-256；不重复定义业务规则。
- `command_manifest.json`：业务批次的三个 preflight 与实际业务命令，或维护批次的固定工具命令。
- `status.json`：原子发布的当前状态，兼容既有字段；保留 `stage_history`、`last_output_at`、`progress_at`；`progress_scopes`、`current_scope_id` 和 `error_summary` 记录可解析的步骤、对象、局部进度与错误摘要。
- `progress.jsonl`：当前批次接受的结构化事件及白名单旧日志事件；完整事件留在文件，status 只保留有界摘要。旧历史可能没有此文件。
- `monitor.pid` / `monitor.json`：可见窗口进程与 UI 刷新心跳；worker 同时核对进程创建时间，防止仅凭复用 PID 判断监控健康。
- `bootstrap.log`、`logs/`、`failure.json`、`control_failure.json`：启动日志、阶段日志与失败证据。
- `interrupt.request`：人工中断证据，重复点击不覆盖。

窗口和后台运行都无需 Codex 回合保持活动。非正常关闭窗口会使监控失效，worker 停止子进程；系统或 worker 崩溃保留锁，等待人工核查。
结束批次耗时固定为 `finished_at - started_at`；旧状态没有阶段明细时显示“旧记录未记录”，不编造完成记录。
`mode: formal` 保留为旧控制协议兼容字段，不表示每个阶段写入正式湖；实际写入意图和目标以 request 中原业务参数为准。
历史查看只读，不能重用旧目录、覆盖旧状态或自动恢复。

`run_history/` 也收纳从草稿区迁入的旧批次，保留原批次名、内部目录和文件内容。2026-08-20 的三批样本失败现场及 2026-08-26 的一批中断现场均在此；文件内的旧路径、PID 和 `running` 状态是当时记录，不代表当前进程存活或任务成功。

完整 stdout/stderr 始终保存在阶段日志。底部按阶段增量读取原文，保留最近 4,000 行，支持跟随末尾及在已加载内容中搜索；显示裁剪不删除文件证据。“阶段日志”弹窗是末尾 256 KiB 的只读快照，持续输出应在底部实时区查看，完整文件可从批次目录打开。进度通道支持带版本、作用域的 JSON 事件，同时对白名单中的旧日志函数、步骤、对象和局部计数作受限解析；不会用任意 `N/M` 推算整个环节完成度。当前没有承诺 19 个入口都已提供统一 JSON 或完整合约/日期剩余量，缺失指标显示未知，旧历史保留原文和已有摘要。

请求接受、转换验收、事实/raw 保存和日历登记是不同进度。正式完成必须依据事务成功退出和该入口要求的完成凭证，不能由日志中一个 `completed`、已安装叶数或持续心跳推断。日历生成计划中的“记录已一致”也不是下游采集完成量；不同步骤的局部计数分别显示，不相互覆盖。

## 保留的执行边界

每个业务批次自动且仅一次按顺序执行：`b00_01_verify_runtime.py`、`runtime/verify_operations_runtime.py`、`b00_02_sync_notebook_exports.py --check --check-level code`。维护任务只运行已确认的工具命令。
启动后每个业务脚本的源码摘要再次核对；选择或预览后源码改变则停止，要求重新创建批次。
