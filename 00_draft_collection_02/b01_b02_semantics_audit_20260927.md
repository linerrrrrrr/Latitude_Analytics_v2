## 当前逻辑与责任边界

| 路径 | b01 交易日历 | b02 品种日历 |
| --- | --- | --- |
| 日常 | 从正式最大自然日的下一天推进到北京时间当前有效日；空湖从配置起点开始 | 从自身最大交易日之后选择 b01 新增交易日；无新增不认证、不请求目录 |
| 来源构建 | 请求一次交易日集合，生成完整自然日区间；休市日保留一行 | 请求一次完整期货证券目录，排除合成连续代码，以固定合约上市闭区间与上游交易日求交、计数 |
| `--full` | 比较完整有效区间，排除 `updated_at`，只提交缺失或修订行 | 比较完整上游主键及有效合约数；有差异的日期按当日完整品种结果替换；超出有效格点的旧主键硬失败 |
| 显式日期 | 成对传入，只读或写入明确不同于正式湖的临时湖 | 同左；只展开上游实际存在的交易日 |

两者的 `--full` 均与显式日期互斥。日常信任已提交历史，历史业务质量与来源一致性检查放在显式全历史路径。
b02 信任 b01 的业务证明，保留上游物理兼容检查，不重复验证上游主键、自然日连续性及派生字段。
事实采集白名单不参与品种日历构建。

提交按以下顺序执行：

1. 验证独立提交输入，再将新结果与触达分区中应保留的旧行合并；对完整替换叶执行业务校验。
2. 写入 staging，逐文件检查字段、类型、nullable、表名/主键/分区身份 metadata，并检查主键唯一性及行数。
3. 在移动旧分区前完成可提前完成的读取。旧分区备份成功后立即登记恢复信息，再安装新分区。
4. 只复读刚安装的叶，逐文件验证物理契约及主键、行数。描述性 metadata 允许不同，不重复完整业务校验。
5. b02 的空结果仍可能删除请求范围内旧行。清空整表时写入零行 `schema.parquet`，正式复读其物理契约与零行数后才成功。
6. 单次提交失败恢复该次已经移动的旧分区；恢复不完整时保留备份。b02 还保留已安装的新分区隔离证据。

事务边界是一次 `commit_partitions()` 调用。b02 的 `--full` 可能按多个日期范围分别调用；后一个范围失败不会撤销前面已成功提交的范围。这是现有执行方式，本轮未改成跨范围事务。

Notebook 的显式入口仍会按示例参数运行；在 Notebook 中导入导出的 Python 模块不会触发入口。
b01 保留 88 个 `=` 与中英文标题，状态行补回 worker 已支持的行首前缀；监控协议没有改变。

## 修复前审计发现（以下均已处理）

### 1. P1：b01 的回滚登记存在数据丢失窗口

位置：[b01](../02_Futures_Lakehouse/a01_Futures_Market_Data/b01_trade_calendar.py) 第 449—456 行；清理路径在第 514—526 行。

旧正式分区先移入 backup，然后打开 staging 叶目录计算行数，最后才追加 `moved_partitions`。如果这次打开或计数失败，已移动的旧分区尚未登记，回滚循环不会恢复它；代码仍报告回滚完成，并删除 backup 与 staging。

复现：临时湖已有 2024 年分区，在旧分区已移动后的 staging 叶打开处注入 OSError。结果为正式分区不存在、备份 Parquet 为 0，日志仍包含 `phase=rollback; status=completed`。

建议：在移动旧分区之前完成可提前完成的读盘 / 行数计算；旧分区移动成功后立即登记恢复信息，登记之前不插入可能失败的操作。增加针对这个窗口的回归测试。

### 2. P2：b01、b02 的提交复读未覆盖所有物理文件

位置：b01 第 384—400、459—475 行；b02 第 560—580、646—665 行。

两者在现有正式表读取时会逐 fragment 验证，但在 staging / 新安装叶验收时主要依赖 `Dataset.schema`，未逐个验证文件的物理 Schema。Dataset 的逻辑 Schema 和后续转换可能掩盖后面文件的安全可转换类型漂移。

复现：把同一叶拆为两个 Parquet 文件，仅改变第二个文件的物理类型并保留值。b01 的 `weekday` 从 int8 改为 int16，b02 的 `active_contract_count` 从 int16 改为 int32。两者均返回成功提交 2 行，下一次正式读取却被既有 fragment 检查拒绝。

这与数据库规则中 staging / 正式安装必须检查物理字段、类型、nullable 及身份 metadata 的要求不一致。

建议：复用现有 `validate_dataset_fragment_schemas()`，分别覆盖本批 staging 和刚安装的叶目录；不增加全表业务重验，也不扩大为 clean 历史扫描。

### 3. P2：b02 的零行 schema marker 未经正式复读验收

位置：b02 第 672—678 行。

初次空表或删除最后一个叶分区时，直接写 `schema.parquet`，随即设置 `commit_succeeded=True`，没有从正式路径重新验证这个文件。

复现：模拟 marker 写入了错误的 `active_contract_count:int32` Schema，函数仍返回 0 并报告提交成功。这里缺少的是空表提交路径的物理契约验收，并非要求空表必须含有业务行。

建议：marker 写入后立即从正式文件验证非分区字段、身份 metadata 和零行数；失败进入现有回滚链路。

### 4. P2：在 Notebook 中 import b01 会自动执行采集入口

位置：b01 第 930—938 行。

入口只判断 `"ipykernel" in sys.modules`。在 Jupyter / PyCharm Notebook 内导入导出模块时，这个条件同样成立，会调用预设日期的 `main.main()`；从定义导入变成发起认证和来源请求。b02 已通过 `"__file__" not in globals()` 区分实际 Notebook 单元格与文件模块，b01 尚未同步。

复现使用入口单元格与模拟 Command，模块导入环境下 b01 的入口调用次数为 1，b02 为 0，没有调用真实 API。

建议：b01 加上与 b02 相同的文件模块排除条件，并覆盖 Notebook 直接执行、脚本执行和 Notebook 内模块导入三种情况。

### 5. P2：b01 的部分主要日志不能刷新 monitor 的 progress

位置：b01 第 694—700、842—847、874—879、889—905 行；worker 第 494—495 行。

问题不是 `=` 分隔线，而是块内只有标题和 `function=...`，缺少 worker 识别的行首前缀。阶段日志文件仍保存全部文字，worker 也仍能记录正常退出；受影响的是实时 `progress` 字段，不能表达全历史检查后的结论。

复现：模拟 `--full` 检查一个已经完整的临时湖。函数退出码为 0，人类可读输出表示“正式交易日历已是最新”，但最后一条可识别进度仍是 `phase=collect; status=completed`。

建议：保留分隔线和标题，为块内状态行恢复 `planning_progress:`、`reconciliation_plan:` 或 `up_to_date:`；b02 当前对应日志已保留这些前缀。

### 6. P2 / 文本冲突：README 仍描述旧的 b02 逐值复读契约

位置：[湖仓 README](../02_Futures_Lakehouse/README.md) 第 309—312 行，与同文第 65—68 行、数据库 AGENTS 第 292—295 行相冲突。

第 312 行仍要求 b02 对 staging / 正式路径“逐值一致性”承担责任，且笼统要求检查现有正式表；当前正式规范已经规定 dirty 完整叶单次业务校验，staging / 正式安装只做物理契约及主键 / 行数摘要，日常信任 clean 历史。

另有 b02 提交函数 docstring 第 249—251 行声称 metadata 与权威 Schema 精确一致，与允许描述性 metadata 差异的实际规则不符。

建议：按既有根规则与数据库规则修正这两处说明，明确现有历史业务审计仅在 `--full` 路径执行；不要为了匹配旧文案重新引入全字段逐值复读。
