# 湖仓分区合并、提交与回滚：抽象可行性审阅

日期：2026-09-27。本文是针对当前代码的分析和候选设计，不是新规范，也未实现或迁移共享模块。

## 结论

可以抽象，而且已有明确的独立责任和真实调用方。最稳定的跨脚本共同责任是：**按明确的替换计划备份旧目标、安装新目标、在正式验收失败时恢复本次变更，并处理本批临时目录与恢复证据。**

“业务合并不同”和“文件提交必须分别实现”不是同一个结论。业务脚本先算出完整替换内容，提交操作面对的就是已准备好的文件、目录及明确的删除动作。不同表名、分区层数、年份/月度粒度本身不构成抽象障碍。

建议先抽取上述安装与回滚操作。Parquet 写入及复读在相同契约的脚本之间也可以进一步共享，但不能把当前所有验收规则、业务合并规则和跨表提交范围一并强制统一。

## 能明确证明的重复

1. a03/b03、b04 的 `commit_complete_fact_partition()`：替换 Schema 名、业务 validator 名和中文提示后，AST 完全相同。业务数据差异没有改变安装与恢复控制流。
2. a04/b02、b03 的 `write_fact_staging()`、`upgrade_fact_metadata()`、`commit_complete_fact_partition()`、`commit_calendar_partition()`：做同样的显式替换后，四组 AST 均完全相同。
3. a01/b05 的 `commit_validated_leaf_group()` 已经把表名、Schema、分区和完整内容作为输入，并在一个恢复范围内提交不同表；这证明共享操作并非依赖假想的未来调用方。
4. a01/b06、a02/b02 的本地 `commit_complete_partition()` 也已经分别服务事实表与日历表。它们的验收契约不同，因此不能未经比较就用其中一个覆盖另一个。

上述 AST 比较只证明所列控制流相同；没有把不同业务 validator 的含义视为相同，也没有把所有接口和性能要求视为一致。

## 抽象边界的建议

### 留在环节脚本里的责任

- 决定本次更新范围：尾部、精确格点、日期区间、完整叶或整根迁移。
- 决定应保留哪些旧行、应删除哪些旧行，以及是否继承质量、完成状态或旁证。
- 构造完整替换结果并执行所属业务规则；共享安装代码不重新推断业务有效性。
- 选择当前契约要求的 staging 和正式验收。已有完整逐值复读不能因为换了共享函数而消失；已迁移的 dirty 叶也不能因此重新增加全表扫描。
- 决定一次共同回滚包含哪些目标，以及业务完成状态何时推进。

### 优先共享的独立操作

输入是本次已经准备并验收过的替换计划，每项至少明确目标路径以及动作：安装指定 staging 文件/目录，或删除指定旧目标。**不能用 staging 路径意外缺失来推断删除。**

共享操作集中负责：

1. 确认本批计划中的目标无重复、无互相覆盖的父子目标，受本次湖目录边界约束。
2. 备份旧目标，记录每项已实际完成的移动，再安装新目标。
3. 将控制权交给调用方的正式验收；验收异常属于本次提交失败。
4. 按本次已完成操作倒序恢复，保留不能恢复的备份，报告原提交错误与恢复错误。
5. 按已确认的现场保留策略清理本批目录，输出提交、验收、恢复的进度。

这是一项完整的、有多个独立调用者的危险文件操作，不是给 `shutil.move()` 套一层名字。业务脚本仍能按顺序直接阅读合并、写 staging、复读及状态更新。

候选调用形态如下，只用于说明责任边界，不是已经选定或实现的 API：

```python
# 本脚本：构造完整输出 → 业务校验 → 写 staging → staging 验收
with replace_staged_paths(replacements, recovery_paths=...):
    # 本脚本：直接保留现有正式复读代码；失败就抛出异常。
    # 共享操作负责在失败时恢复本次目标，成功时完成清理。
    ...
# 本脚本：按原有时点汇总结果或推进完成状态。
```

如果采用这种上下文形态，共享实现必须连进入上下文本身的备份/安装失败也一并回滚，不能只依赖上下文退出时处理异常。业务异常不能被吞掉；回滚未完成的备份不能被通用 finally 清理。

### 可以进一步共享、但不应与第一步混做的内容

- 同一验收契约下的完整 Parquet 叶写入、物理复读和主键/内容摘要验收，例如已经确认同构的 a03/b03—b04 或 a04/b02—b03。
- 相同 Schema 兼容规则。这是项目不变量，值得共享；但“身份 metadata 兼容”与“精确 metadata”必须按当前适用契约区分。
- 这些能力不要求做成类层次、注册表、通用存储服务或一套由脚本编号决定行为的框架。先有一个明确的安装/恢复边界，已足以收敛最容易发生修复漂移的代码。

## 真正的难点及处理方式

### 1. 事务范围必须由调用方保留

单叶是一个目标，多叶是一组目标；整根也是一个目录目标。因此路径层面可以统一。但是：

- b05 的事实叶与日历叶必须属于同一组；b08 的缺失表根与日历叶也必须属于同一组。
- b06、a02/b02—b03、a03/b02—b04、a04/b02—b03 现有先后独立提交必须保持独立调用。后一次失败不撤销前一次已经成功的结果。
- b03 的自动处理水位仍在原有时点独立更新；不能因为 marker 也叫 `schema.parquet` 就跟空表初始化合并。

抽象不会自动提供跨目录的瞬时原子可见性、持久事务日志或自动恢复；本轮不需要顺带建设这些机制。

### 2. 空结果至少有四种不同含义

- 无待办，不调用共享提交，例如 b01 空输入。
- 清退已有叶，例如 b02、仓单、外部指数的完整替换空结果。
- 保留一个真正的零行叶文件，例如 b06。
- 不允许空叶，例如 b05 日常提交、a04 日历回写。

业务层需要先确定含义，再形成明确的文件操作计划。共享层不需要知道“交易日”或“Session”。

### 3. marker 是受管理输出的一部分，不是通用补丁

有的入口只在整表为空时建 marker，有的始终要求 marker；b04 会备份替换旧 marker；b03 marker 含水位。需要新建/替换/删除的 marker 必须进入恢复计划，既有不变 marker 不应被重写。把所有入口统一为“提交后补一个空 marker”会改变语义。

### 4. 复读规则不能擅自统一

当前代码至少存在：物理契约 + 行数/主键唯一；物理契约 + 排序主键摘要；完整值比较或内容摘要；表根级总量和分区集合校验。它们有各自现行契约。

第一步把这些验收留在调用方，使验收异常触发同一个共享回滚即可。后续在契约一致的调用方之间抽取完整叶提交，不必一次增加大量布尔开关。

### 5. 失败后的现场保留目前确实不同

b01 恢复时删除新叶；b02—b06 中若干入口在成功恢复旧叶后仍保留新叶隔离证据；b07 和部分其他组在恢复成功后清理隔离目录；恢复失败通常保留备份，但清理时点并不完全相同。

这些差异有的属于已采用的操作方式，有的只是实现写法分歧。迁移时应明确哪些应保留、哪些应统一，不应把每个历史写法都变成永久参数，也不应以共享函数默认值悄悄修改。

### 6. 保持运行成本和返回语义

b08 已按叶生成 staging，共享操作应能接收已落盘目标，不能要求把全量明细重新载入内存。其他调用方也应保留当前只读 dirty 叶的边界。

有的函数返回输入行数，有的返回完整分区 DataFrame，有的返回多个计数。共享安装操作只报告自己的提交结果；原有业务返回值、事实计数和日历状态时点由调用方维持，不能混成一个含义不明的 `rows`。

## 为什么这次值得抽象

不仅是文本重复：同一种安装和恢复责任已经出现多份实现。部分版本记录 `old_target_moved/new_target_installed`，部分版本主要依赖路径存在性；marker 恢复和失败证据清理也各自维护。对公共恢复规则的修正无法自然覆盖其他入口，这已经构成具体维护成本。

反过来，十几行“保留范围外旧行，再 concat 新行”的业务合并即使看起来类似，也没有必要为了消除文本重复造一个合并策略框架。具体替换集合直接写在所属环节，通常更容易核对。

## 迁移顺序与验证依据

1. 先明确共享安装/恢复的输入、失败现场策略和 marker 处理，保持所有现有业务验收契约。新模块先放草稿区，正式归属按项目规则确认后再提升。
2. 按原逐脚本节奏先迁移 b01、b02：分别验证按主键合并、按闭区间完整替换，确认范围外行和同组其他叶的行为不变。
